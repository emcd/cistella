## Context

Proven live 2026-09-18 (scratch `default`-profile sessions, since torn down): `podman exec` runs as uid 1000; a triple targeting `/home/cistella/.config/deep/nest` yields root-owned `.config` and `.config/deep` with a me-owned `nest`; `mkdir /home/cistella/.config/agentmux` as the seat fails `Permission denied`. No `--user` exists anywhere in driver code or the image — the 1000 default is observed podman behavior, not a contract. The conduct flow (`conduct_session`, `src/main.rs:244-446`) already has the shape this needs: lock-guarded creation window, fail-closed teardown after install/start, harness attach last.

## Goals / Non-Goals

**Goals:**
- Sessions can create sibling dirs under auto-created mount parents, for seat-owned work, without per-dir triples.
- Never alter host-side ownership (mount roots are a hard boundary), never touch `/`, idempotent re-runs.

**Non-Goals:**
- No pinning of the harness exec user (transport follow-up, separate change).
- No changes to tmpfs home handling (arrives 1777, works; document, don't touch).
- No profile schema or CLI surface changes.

## Decisions

- **Prepare after start, before harness attach, inside the creation-window lock.** The container must exist (exec needs it running); the harness must not race preparation. The lock already spans install→start; extending through a bounded exec sequence keeps `gc`/`terminate` from observing a half-prepared session. Alternative considered: host-side `podman unshare mkdir/chown` before start — rejected because host-side ownership is the wrong namespace to reason in (keep-id maps container-1000↔host-1000, but podman-created parents' host ownership is an implementation detail we should not depend on); in-container preparation sees exactly what the seat sees.
- **Read the seat uid live (`podman exec <ctr> id -u`).** Alternative considered: assume 1000 from keep-id — rejected; the whole bug class comes from assuming uid behavior instead of measuring it.
- **Pin `--user root` on setup execs.** The observed exec default (1000) would make mkdir/chown silently ineffective; explicit root keeps setup effective even if podman changes its default. Seat-uid chown target comes from the live read, so the two never drift.
- **Conditional chown (only uid-0 dirs), unconditional mkdir -p, batched execs.** Chown is conditional on root ownership rather than createdness: podman pre-creates missing parents before preparation runs, so "absent before mkdir" would spare exactly the dirs this step exists to fix (proven live: the stat-before variant prepared nothing). Converging root-owned container-local ancestors seat-owned is safe — per-session upper destroyed at teardown, modes preserved by chown, bind mounts and `/` structurally excluded. The walk stops at the tmpfs home (never ascends above it for under-home targets), so image directories outside every target chain are not even candidates. Execs are batched, not per-directory: one uid read, one `realpath -m` resolve over all computed ancestors, then one `mkdir -p` over the authorized set, one `stat` over the same set, then (only if root-owned entries remain) one `chown` over that subset — five bounded execs worst case, each explicitly deadlined. Mountpoint ancestors (all triple targets, tmpfs home, session-home target) and `/` are excluded before any exec — computed purely from the profile + session, unit-tested without podman.
- **Canonical bind set from emitted volumes, not raw profile strings.** Authorization consumes `volume_targets(all_volumes)` — the container side of every emitted `--volume` entry (profile, CLI, session-directory, scratch, and credential-surface volumes alike) in canonicalized form. A noncanonical profile spelling can therefore never desynchronize the predicate from the real mount prefix; the credential socket's ancestors are covered by the same rule. Candidates are seeded separately by `preparation_sources` (next bullet).
- **Runtime containment proof per candidate; lexical walk stays as candidate generation only.** Each lexical candidate is resolved in-container, and so is every bind target: authorization compares resolved-against-resolved, so image-baked symlink components in a bind target cannot hide a host-backed path behind a lexical mismatch. Admission control bounds the threat: nesting a target under any triple is an overlap violation, so a container-side alias into a bind cannot be admitted through profiles at all — the refusal path covers image-baked symlinks (proven by unit tests; no live form exists with current images) and any future admission gap, failing closed before any mkdir/chown.
- **Candidate sources are user mounts; the authorization set is every emitted bind.** `preparation_sources` (profile + CLI + session triples, canonicalized) seeds candidates; `volume_targets` (profile/CLI/session/scratch/credential volumes, canonicalized) authorizes them. Internal primitives therefore never trigger ownership changes to shallow system ancestors: `/run` and `/tmp` are pinned untouched by live assertions, and the split is unit-tested.
- **Lexical beneath-bind exclusion is silent; runtime refusal is fail-closed.** Paths lexically beneath a known bind target are dropped from the candidate set without error — legitimate topology, since `validate_mounts` permits descendant mounts under read-only ancestors (the tmpfs-home subtree stays eligible as container-ephemeral). But every lexical candidate is clean by construction, so a *resolved* beneath-bind path means resolution revealed a bind the strings did not know (symlink alias): the whole preparation — and therefore the conduct — fails with a typed error before any mkdir/chown. Skip-and-continue is never an option at the runtime stage. Nested-RO exclusion and tmpfs-home eligibility are pinned by unit and live cases.
- **Fail closed through the lock-held teardown form.** Preparation runs under the creation-window lock, so its failures must call the lock-held inner teardown (`teardown_inner`), never the lock-acquiring `teardown` — re-acquiring the held lock would deadlock the very path that guarantees no residue.
- **Setup exec discipline: argument vectors with `--` before paths, one bounded numeric UID parse, explicitly bounded execs.** Paths never transit through shell strings; the live `id -u` read parses as a single bounded integer (anything else is a typed error, not a default); every spawned exec carries an explicit deadline inside the existing bounded-exec discipline.
- **Setup binaries resolve from the selected image while running as container root.** Documented as assumed authority: preparation `id`/`realpath`/`stat`/`mkdir`/`chown` are whatever the image ships. If images ever stop being a trusted boundary, this step gains authority over RW mounts and needs re-review — recorded here so that day is a conscious decision, not drift.
- **Same-exec proof: amendment requested, narrower invariant stated.** Resolve-then-mutate across execs leaves a dynamic symlink-swap window that coreutils cannot close without a descriptor walk or an image-assumed interpreter. The stated invariant: between container start and harness attach the only writers to container paths are podman setup (completed before start returns) and this step's own execs — no untrusted actor exists in that window, because images are already the recorded trusted authority for root-executed setup binaries. Under that invariant a swap requires a compromised image, against which the harness itself (following the same links) is equally exposed — so the residual risk is not preparation-specific. Static symlinks (the reachable case) are fully covered: resolved-path operation plus fail-closed refusal, proven by unit tests. If tier-2 rejects the amendment, the fallback is a single `python3` descriptor-walk exec gated on image capability, which the design does not take now.
- **Timeout bound is teardown completion, not the host kill.** `run_deadline` SIGKILLs the host `podman exec` client, but a disconnected client can leave the container-side process running — so the claimed wall-clock bound is established one level up: every preparation error (including deadline breach) runs full `teardown_inner` before conduct reports, and no in-container exec outlives its container's removal. A forced-timeout live test (1 ms deadline) proves conduct fails with the deadline error and zero residue.

## Risks / Trade-offs

- [Risk] `podman exec` flakiness under load fails conducts that would otherwise start → Mitigation: preparation is five bounded execs worst case (uid, resolve, mkdir, stat, conditional chown); failures tear down loudly rather than stranding sessions, and the live tests guard the path.
- [Risk] Chowning an ancestor the image deliberately owns root (setuid helpers, system dirs under home?) → Mitigation: the walk stops at the tmpfs home (never ascends above it), mountpoints and `/` are excluded, and only root-owned entries converge — pre-existing non-root ownership is never touched. Container-local convergence is per-session ephemeral with modes preserved; image system dirs outside every target chain are not candidates at all.
- [Risk] Future podman changes parent-creation ownership (e.g. creates as seat user) → Mitigation: conditional chown becomes a no-op naturally; mkdir -p stays harmless. The step degrades to redundant, never wrong.
- [Risk] RO-target parents gaining creation rights surprises authors → Mitigation: normative delta sentence — RO applies to the mounted subtree, which is never chowned; only the non-mounted ancestor chain gains traversal/creation rights as traversal infrastructure.
- [Risk] Parse-time rejection of nested-under-RO targets would fail fast instead of crash-looping → Mitigation (deferred, consciously): the session-directory triple routinely nests under RO profile triples with host-preexisting intermediates (the working dogfood shape), which a string rule cannot distinguish from the broken case; rejecting would break working sessions. Revisit only with a mount dry-run capability.
